## Hallazgos confirmados que bloquean producción

### Críticos

- **DB-01 — ACL amplias; acceso REST condicionado por Data API:** las 18 tablas `public` tienen RLS y ninguna `FORCE RLS`; los catálogos conceden `TRUNCATE` a `anon` y `authenticated` en las 18. RLS no limita `TRUNCATE`, pero PostgREST no lo expone como operación REST directa. Además, PostgreSQL concede CRUD a `anon`/`authenticated` en varias tablas y CRUD a `anon` en `trade_offers`; son privilegios efectivos a nivel de base de datos, no prueba de que todas esas tablas sean accesibles por REST. La verificación posterior de Data API (DB-20) muestra solo 5 de 18 tablas expuestas, por lo que las tablas no publicadas no se consideran rutas HTTP confirmadas. Las grants restantes siguen siendo privilegios excesivos/latentes ante publicación futura, RPC u otra vía SQL. Las migraciones C/E no cubren el conjunto ni deben tratarse como hardening global.
- **DB-02 — Política pública en salas no expuestas por Data API:** `chat_rooms` tiene `SELECT TO public USING (true)` y ACL de lectura anon, pero DB-20 confirma que la tabla no está entre las cinco expuestas actualmente por Data API. Por tanto, esta política no demuestra lectura REST pública efectiva en el estado revisado; sigue siendo una exposición latente si la tabla se publica o se añade otra ruta. El cliente intenta leer salas y filtra después, pero la consulta estática no prueba que la petición tenga éxito.
- **DB-03 — Inserción permisiva en salas, ruta REST no publicada:** `chat_rooms` conserva política `INSERT TO authenticated WITH CHECK (true)`, además de políticas de participante. Permitiría filas con IDs ajenos si se concede acceso por una ruta compatible, pero DB-20 indica que hoy no está expuesta por Data API; no se probó ni se afirma una inserción HTTP efectiva.
- **DB-04 — RPC privilegiada con autorización débil; no publicada actualmente:** `finalizar_trueque_atomico(uuid,text)` es `SECURITY DEFINER`, ACL permite `EXECUTE` a `anon`, no fija `search_path`, no rechaza explícitamente `auth.uid() IS NULL` y admite cualquier `p_new_status`. En PL/pgSQL, una condición `IF` cuyo resultado sea NULL puede omitir el rechazo. Sin embargo, DB-20 confirma que la función no está entre las tres funciones expuestas por Data API; no se ha demostrado invocación anónima por REST en el estado actual. Mantenerla como hallazgo prioritario de ACL/lógica y riesgo latente antes de cualquier publicación o cambio de exposición; nunca invocada durante esta auditoría.
- **SEC-01 — Clave HMAC incrustada en SQL:** la función remota `notify_trueke_status_change` contiene una clave literal dentro de su cuerpo. Se considera expuesta y requiere rotación coordinada y eliminación del literal. El valor no se reproduce en este informe. La migración local que la introduce también contiene el literal.
- **PAY-01 — Estado de pago simulado en cliente:** `PaymentNotifier` inventa un identificador `mock_intent_…` y marca la orden como `succeeded` sin confirmar un cobro real. No se debe habilitar este flujo como pago productivo.
- **PAY-02 — Webhook Stripe local sin firma:** `supabase/functions/stripe-webhook/index.ts` usa `SUPABASE_SERVICE_ROLE_KEY` para mutar escrow, pero no verifica firma/evento Stripe. `supabase/config.toml` tiene `verify_jwt = false`. No está desplegada actualmente; la lista remota no la incluye. Mantenerla sin desplegar hasta repararla.

### Seguridad y privacidad altas

- **DB-05 — Políticas permisivas y exposición desigual:** `notifications` está expuesta por Data API y permite `INSERT WITH CHECK (true)` a cualquier `authenticated`; la combinación ACL/RLS permite crear notificaciones con destinatarios que el cliente pueda asignar. `favorites` (lectura pública) y `truekes` (políticas de lectura autenticadas duplicadas) no están expuestas actualmente por Data API según DB-20; esos permisos son riesgos latentes de política, no lecturas REST demostradas. Se encontraron duplicados/antiguas en productos, perfiles y ofertas, que deben evaluarse solo después de confirmar exposición y ACL.
- **DB-06 — Privilegios de tablas financieras:** la ACL permite `TRUNCATE` a `anon` y `authenticated` en `escrow_transactions`, `transactions`, `trueke_disputes`, `trueke_escrow_ledger`, `trueke_payment_orders` y `truekes`, aunque el acceso CRUD ordinario sea más restringido. Como se indica en DB-01, la consulta no demuestra una ruta REST directa para ejecutar `TRUNCATE`; requiere análisis de cualquier función SQL con privilegios elevados.
- **DB-07 — Mutación de escrow con invariantes tautológicas:** las políticas `WITH CHECK` de reembolso/envío comparan campos con ellos mismos (`id = id`, `amount = amount`, etc.); no preservan necesariamente valores anteriores. Requiere rediseño con restricciones/funciones transaccionales antes de usar dinero real.
- **DB-08 — Activación de oferta falla por trigger divergente:** `on_trade_offer_accepted_sync` accede a `sender_product_id` y `receiver_product_id`, ausentes de la tabla remota `trade_offers`. Hay dos triggers de aceptación distintos y el modelo remoto mezcla pares `from_user_id/to_user_id` con `sender_id/receiver_id`. La aceptación puede fallar y no hay una única fuente de verdad del ciclo de oferta.
- **DB-09 — Reputación y disputas:** los triggers remotos `handle_recalculate_user_reputation` y `handle_dispute_reputation_penalty` actualizan `profiles.reputation` y/o consultan `user_reviews.reviewed_user_id`; esas columnas no existen en el esquema remoto. Las reseñas tienen dos triggers de recálculo duplicados.
- **DB-10 — Funciones privilegiadas sin endurecimiento uniforme:** varias funciones `SECURITY DEFINER` tienen `search_path` nulo o `public` y ACL `EXECUTE` amplia. DB-20 confirma que solo 3 de 19 funciones aparecen expuestas por Data API y que son `handle_new_user`, `validate_trade_offer_insert` y `validate_trade_offer_update`, todas vinculadas a triggers y no RPC normales llamables mediante PostgREST. Los RPC de negocio detectados por catálogo no están publicados actualmente. Riesgo de configuración/ACL y de publicación futura; no afirmar explotación REST sin endpoint y prueba autorizada.
- **PRIV-01 — Coordenadas de productos publicadas:** `products` sí figura entre las cinco tablas expuestas por Data API, tiene lectura pública y contiene `latitude`, `longitude` y `geo_location`; por tanto, los campos de ubicación que incluya el `SELECT` pueden quedar disponibles a clientes anon. Los RPC de búsqueda no están expuestos actualmente y no se cuentan como ruta HTTP actual. Debe revisarse si la API devuelve ubicación precisa y si el producto requiere generalizarla.
- **PRIV-02 — Eliminación de cuenta no implementada:** `delete-account.html` solo muestra un `alert` y cancela el envío; `AuthService` no tiene operación de borrado y no se desplegó función de administración de cuentas. El texto promete eliminación en 48 horas y la política afirma que se puede eliminar desde ajustes, sin flujo real localizado.
- **PRIV-03 — Caché entre usuarios:** `LocalTruekeDataSource` guarda todos los trueques bajo una clave global no ligada al usuario y `signOut()` no la elimina. Si la siguiente sesión queda sin red, puede mostrar datos de la sesión anterior. El búfer estático de chat también carece de limpieza al cerrar sesión.
- **PRIV-04 — Telemetría de IP:** la función pública Asset Links registra IP reenviada y agente de usuario en los logs. La política de privacidad local no describe ese registro ni los servicios de mapas/teselas observados. No se evalúa aquí cumplimiento jurídico; el texto requiere revisión frente al comportamiento efectivo.
- **PRIV-05 — Datos financieros visibles en contratos cliente:** los modelos locales conservan importes, identificadores externos y estados, pero los permisos remotos de tablas de pago no habilitan el flujo cliente que pretenden usar. Debe evitarse que el cliente sea autoridad del estado financiero.

## Integración Flutter ↔ Supabase: errores funcionales confirmados

- **DB contract:** la app consulta `reviews`, `disputes`, `payment_orders` y `user_wallets`; el esquema remoto no tiene esas tablas. Existen `user_reviews`, `trueke_disputes` y `trueke_payment_orders`; no se encontraron `user_wallets` ni la función RPC `deposit_wallet_funds`.
- **Stripe Connect:** Flutter invoca `create-stripe-connect-account` e `initialize-mixed-payment`; no existen entre las Edge Functions locales ni las dos desplegadas.
- **Productos:** el esquema remoto tiene `images`, pero el modelo `Product.toJson()` emite `image_urls`. El valor por defecto remoto de `products.status` es `available`, mientras las búsquedas RPC/REST filtran `active`. La paginación geográfica añade `page_offset/page_limit`, argumentos que no están en la firma remota. El fallback de búsqueda contiene una regla fija para “mando/PS5” y devuelve productos sin comprobar su distancia real.
- **Perfiles:** la tabla remota solo tiene `id, username, display_name, avatar_url, created_at, updated_at, average_rating, total_ratings`. Flutter envía/actualiza también `email` y `bio`, columnas ausentes.
- **Chat:** la tabla remota `chat_messages` no contiene `offer_id`, `is_system`, `is_read` ni `is_delivered`; el repositorio los envía e ignora errores, dejando mensajes solo en memoria. No existe el bucket Storage `chat_attachments`; al fallar la subida se devuelve una URL pública de Picsum.
- **Ofertas y conversaciones:** coexisten `conversations/messages` y `chat_rooms/chat_messages`, con repositorios Flutter distintos. El RPC `create_trade_offer` escribe en la primera pareja; el chat visible usa la segunda. El modelo de ofertas y varias consultas directas usan columnas inexistentes (`sender_product_id`, `receiver_product_id`, `additional_cash`) o pares de IDs distintos.
- **Transacciones:** el cliente escribe directamente en `transactions`, pero `authenticated` no tiene los privilegios ordinarios observados; el RPC `finalizar_trueque_atomico` del cliente envía parámetros diferentes a su firma remota.
- **Escrow:** el repositorio intenta insertar/actualizar directamente `escrow_transactions`, pero los privilegios CRUD remotos observados no lo permiten. El trigger de estado de `truekes` actualiza el libro `trueke_escrow_ledger`, otra ruta distinta del modelo de escrow Stripe.
- **Disputas:** el repositorio usa `disputes`; la tabla real es `trueke_disputes`.
- **Reseñas:** el repositorio de lectura `features/reviews` consulta `reviews`, tabla inexistente. Los dos lectores de `user_reviews` se ajustaron localmente a `display_name` tras verificar el esquema; el escritor añade `reviewer_name/reviewer_avatar`, ausentes remotamente, y el modelo espera `trueke_id`, también ausente. La inserción RLS solo comprueba identidad del reseñador, no un trueque finalizado.
- **Soporte:** Flutter consulta `reports`; no se encontró esa tabla en el esquema remoto.
- **Favoritos:** el repositorio requiere `INSERT/DELETE`, pero el ACL remoto no concede esos permisos; la migración E pendiente los propone y elimina la política pública.
- **Tokens push:** el ACL remoto no habilita el CRUD usado por el cliente; la migración C pendiente lo propone. Sin embargo, el lector de tokens en Edge usa la clave anon y el Authorization recibido, mientras RLS solo permite al propietario leer su token; no resuelve la lectura del destinatario desde un trigger.

## Storage, soporte, ajustes y sesión

- **ST-01 — Borrado de imágenes:** la fuente local permite borrar imágenes de producto y avatares, pero la consulta remota de `storage.objects` no encontró políticas `DELETE` para esos buckets. Las operaciones de eliminación fallarán aunque la interfaz las intente. El bucket `product-images` tiene lectura pública, carga de propietario, límite de 5 MiB y MIME `image/*`; `avatars` es público y no tiene límite ni MIME restringido. Las políticas de carga/actualización de avatar aparecen duplicadas.
- **ST-02 — Adjuntos de chat:** la app sube a `chat_attachments`, bucket ausente. El fallo se oculta y la función devuelve `https://picsum.photos`, así que el chat puede mostrar contenido que no corresponde a la imagen seleccionada.
- **SUP-01 — Informes de soporte:** el repositorio usa `reports`, tabla ausente del esquema remoto. El envío y la consulta de informes no tienen backend compatible.
- **SET-01 — Preferencia de push sin efecto:** el interruptor `pushNotificationsEnabled` se guarda en SharedPreferences, pero `pushNotificationsSyncProvider` pide permisos y sincroniza tokens sin consultar esa preferencia. Desactivar la opción en ajustes no garantiza que se detenga la sincronización.
- **AUTH-01 — Sesión y datos en caché:** el caché de trueques tiene una clave fija compartida entre cuentas y el cierre de sesión no la limpia; el búfer de mensajes también es estático y no se vacía. Revisar además el comportamiento offline al cambiar de cuenta.
- **LOC-01 — Ubicación:** el servicio solicita precisión alta y envía coordenadas exactas a búsquedas/filas. El listado público de productos expone coordenadas y las vistas de mapas las usan directamente. La política de privacidad local no describe claramente esta exposición ni el acceso a los servicios de mapas/teselas.

Estos hallazgos se añaden al inventario; no se aplicaron cambios de Storage ni de aplicación durante esta ampliación de auditoría.

## Matriz RLS por operación y rol (consulta remota de solo lectura, 2026-10-16)

Se consultó `pg_policies` por tabla, comando, rol, modo permisivo y presencia de expresiones incondicionales/`auth.uid()`. No se leyeron filas de usuarios. En PostgreSQL las políticas `PERMISSIVE` se combinan mediante OR; una política `true` puede anular el filtro de otra política para el mismo rol/operación.

- **DB-11 — Lecturas sin filtro en tablas no publicadas:** políticas `SELECT true` en `chat_rooms` (public), `favorites` (public), `profiles` (authenticated), `truekes` (dos políticas authenticated) y `user_reviews` (public) permitirían lectura amplia si las tablas se exponen por Data API u otra ruta. - **DB-13 — Duplicación permisiva de productos y ofertas:** `products` tiene tres políticas `SELECT` incondicionales (roles `public`, `anon,authenticated` y `authenticated`), además de políticas repetidas de `INSERT`, `UPDATE` y `DELETE`. `trade_offers` tiene tres políticas de lectura autenticadas y varias políticas solapadas de inserción/actualización, además de políticas `public`; al ser permisivas, su unión efectiva debe revisarse campo por campo, no juzgando cada regla de forma aislada.
